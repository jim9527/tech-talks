AI 测试工作坊

使用 AI 做测试：以 E2E 为重点

AI 现在已经很擅长生成单元测试和集成测试。 真正更难、也更值得展开讨论的是，如何把它用好在端到端测试上。

这场分享从更大的主题 AI for testing 出发， 然后聚焦到摩擦最高的一层： 结构化提示词 → AI Agent / MCP → 生成 Playwright 测试 → 执行 → 评审 → 接入 CI。

关注点：当 AI 在 unit test 和 integration test 上已经表现不错时，还需要补上哪些工程纪律，才能让它真正适用于 E2E。
工作坊目标

给出一套务实的工作模式：如何借助 AI 生成、评审并规模化自动化测试，同时不降低质量标准。

目标听众

适合已经在采用 AI 辅助测试编写、但又不希望降低工程标准的技术团队。

案例选择

主案例使用本地仓库里的 scholarship 流程，而不是只依赖一个玩具型 demo。

核心观点

AI 是测试交付的放大器，但在 E2E 这一层，流程设计和工程判断仍然最关键。

1. 分享框架

分享框架

更大的主题

这次分享的主题是 如何使用 AI 做软件测试，而不只是如何写 Playwright 代码。 重点是讲清楚：AI 在哪些地方能明显加速测试工作，哪些地方仍然必须依赖人的判断。

为什么重点讲 E2E

AI 已经很擅长生成 unit tests 和 integration tests，因为这些层级通常范围更小、输入更清晰、UI 不确定性也更少。 E2E 依然是最贵、最复杂、也最具战略价值的一层。

这场分享的重点不只是“AI 会写测试”。 更准确的说法是： “AI 在整个测试栈里都能帮忙，但在 E2E 这一层，一个更好的工作流能带来最大的收益。”

2. 为什么是 E2E

为什么 E2E 依然重要

逻辑

单元测试 验证的是局部逻辑是否正确，但它无法说明真实用户能不能完成整条流程。

契约

集成测试 能捕捉模块或服务边界的问题，但依然无法覆盖浏览器行为和完整业务流程。

结果

E2E 测试 验证的是真实用户旅程能否从 UI 意图一路走到后端结果。

如果业务价值是“一个 manager 可以创建 scholarship”，那么最有信号的测试， 就应该直接验证这条流程，而不只是去测某个 reducer 或 API client。

3. 成本

为什么传统 E2E 让人觉得昂贵

常见失败模式

  • 脆弱的 selector 让测试依赖样式细节，而不是依赖稳定意图。
  • 登录、造数、初始化步骤在每个 spec 里反复复制。
  • 异步行为带来竞争条件、重试和误报。
  • 团队大量时间花在修测试，而不是扩充覆盖面。

团队真正付出的成本

  • 大量模板化、重复性的编写时间。
  • 重复准备步骤导致反馈周期变慢。
  • 无害的 UI 重构也会带来额外维护成本。
  • CI 噪音过高，削弱团队对测试套件的信任。
问题并不在于 E2E 这个理念本身错了，而在于传统写法在工程上不够省力、也不够稳定。
4. AI 改变了什么

AI 改变的是成本曲线，不是质量定义

AI 擅长的事

  • 把结构化需求快速转成 Playwright 测试骨架。
  • 自动补齐重复性的浏览器步骤和断言。
  • 按既有规范重构已有 spec。
  • 在拿到 trace 和上下文后，协助迭代修复失败用例。

AI 不能替代的事

  • 决定哪条业务流程最值得保护。
  • 决定什么样的失败应该阻断发布。
  • 保证生成的 selector 一定真实存在。
  • 判断这条测试到底有没有验证到真实业务价值。
这里的关键结论是：AI 确实降低了编写和维护成本，但工程判断仍然是控制平面。
5. 优势与限制

AI 驱动 E2E 测试的优势与限制

优势

  • 速度： 通过结构化 prompt 生成代码，写测试会快很多。
  • 准确性： AI 能输出更一致的 Playwright 语法，减少日常模板性错误。
  • 覆盖率： 编写成本下降后，更容易补更多场景，扩大覆盖面。
  • 门槛更低： 当 prompt 和团队约定足够清晰时，对 Playwright 细节的依赖会降低。
  • 标准化： 生成测试更容易遵循统一格式、规范和团队实践。

限制

  • Prompt 质量： 输入模糊，输出通常也会模糊甚至错误。
  • 学习成本： 仍然需要懂 E2E 原理，也要会写有效的 prompt。
  • 工具边界： 结果会受到 MCP 工具和底层 LLM 能力的限制。
  • 调试： 复杂失败依然需要 Playwright 和浏览器行为方面的人类经验。
  • 过度依赖： 生成测试之后，review、验证和长期维护仍然不可省略。
最实用的模式很简单：用 AI 降低测试编写成本，但测试意图、调试和发布信心依旧由人负责。
6. 工作流

AI 辅助的 E2E 工作流

01
结构化提示词

把功能、目标、步骤、数据和预期结果描述到足够清楚，让 agent 不需要靠猜。

02
AI Agent / MCP

借助浏览器感知能力去理解页面，再生成真实可执行的 Playwright 代码，而不是伪自动化。

03
生成 Spec

最终输出仍然应该是标准 TypeScript Playwright 测试，方便工程师阅读、编辑和评审。

04
执行

在真实应用上运行，检查失败、核验 selector、等待逻辑和业务断言是否正确。

05
人工评审

确认测试保护的是正确流程，而不是把脆弱、误导性的假设编码进去了。

06
CI / 发布门禁

把测试接入持续运行流程，让它成为真实的发布护栏，而不是一次性的实验。

真正的变化不是“AI 会写一个测试”，而是“AI 缩短了从需求到可执行、可评审测试代码的路径”。
7. Prompt 质量

Prompt 质量会直接变成测试质量

弱 Prompt

请帮我给 scholarships 写一个 Playwright 测试。
结果通常会很泛，容易猜 selector，也容易漏掉关键断言。

更有用的 Prompt

我需要用 Playwright MCP 创建一个 E2E 测试。

功能：Scholarship 创建
目标：District manager 可以成功创建一个 scholarship
入口状态：用户已登录
路径：/scholarships/new
输入：
  - 名称：Test Scholarship
  - 金额：5000
  - 截止日期：12/31/2026
断言：
  - 提交成功
  - 页面跳转到 /scholarships
  - 如果列表页展示该记录，则应可见
约束：
  - 优先使用 getByRole / getByLabel
  - 能复用 storageState 就复用
应该包含

目标、角色、入口状态、关键输入、预期结果，以及 selector 偏好。

不要假设

不要假设模型天然知道项目里的认证方式、路由约定或者表单语义。

8. Prompt 示例

不同测试层级下的 Prompt 形态

Unit / Integration 风格 Prompt

所有新增代码都应该配套单元测试。

新增功能时：
* 为新模块创建测试文件，验证核心行为
* 为工具函数补 happy path 测试
* 在适用场景下补 edge cases 和不同输入类型

典型目标：
- 推断函数行为
- 补齐边界场景
- 生成 table-driven tests
- 在需要时 mock 依赖
AI 在这一层通常表现很好，因为逻辑通常是 deterministic 且 isolated 的，更容易推断函数行为、补 edge cases、生成 table-driven tests，也更容易把依赖 mock 对。

E2E 风格 Prompt

功能：创建 Scholarship
目标：District manager 可以提交一个新的 scholarship
类型：端到端测试
前置条件：
  - 通过 storageState 进入已登录状态
路径：
  - /scholarships/new
步骤：
  1. 填写 scholarship 名称
  2. 填写金额
  3. 填写截止日期
  4. 点击 Add Scholarship
断言：
  - 最终跳转到 /scholarships
  - 不应出现校验错误
约束：
  - 优先使用可访问性 selector
  - 避免任意等待
同一个模型在不同测试层级上的表现会不一样。E2E prompt 需要更多上下文，因为浏览器状态、selector 质量和业务流程语义都会影响结果。
9. 可复用模板

Playwright MCP Prompt 模板

我需要使用 Playwright MCP 创建一个 E2E 测试。
请帮我生成一个可以加入现有测试套件的测试脚本。

测试信息：
- 要测试的功能：[功能名称]
- 测试描述：[简要描述]
- Base URL：[应用地址]
- 测试步骤：
  1. 进入 [登录地址或目标页面]
  2. 输入账号密码并点击登录按钮
  3. 点击 “Create New” 按钮
  4. 完成实体配置、填写字段并做必要选择
  5. 点击 Next
  6. 输入查询文本或业务输入
  7. 如有需要，调整滑块或高级配置
  8. 点击 CREATE
  9. 判断 modal 是否出现
  10. 如果出现再处理 modal
  11. 等待创建结果可见
  12. 如有需要，从测试目录中上传文件

重要要求：
- 使用 Playwright MCP 生成测试代码
- 对复杂逻辑添加注释
- 测试结束后确保关闭浏览器
- 在适当位置包含超时和错误处理

保存到：
- 路径：[tests]/[my_feature_test].spec.ts
- 测试名称："Validate My Feature"
用途

这个模板的价值在于，一次性把目标流程、状态假设、分支行为、保存路径和质量约束都讲清楚。

如何改写

结构保持稳定，只替换功能名、路由、动作、数据值和预期结果，就可以快速复用到不同场景。

10. 真实案例

让整场分享落在真实业务流程上

仓库中的实际例子

  • e2e-demo/tests/scholarship.spec.ts 已经覆盖了 scholarship 创建流程。
  • 这个流程对应一个真实的内部角色：district manager。
  • 断言验证了提交后的跳转结果，也体现了真实表单交互的复杂度。
  • 相比只讲公开 catalog demo，这种叙事更有说服力。

当前 Spec 形态

test('user can create a scholarship with storage state', async ({ page }) => {
  await ensureLoggedIn(page);

  await page.getByRole('textbox', { name: 'Name of Scholarship *' })
    .fill('Test Scholarship');
  await page.locator('#mui-9').fill('5000');
  await page.getByRole('group', { name: 'Application Due Date' })
    .getByLabel('Application Due Date *')
    .fill('12/31/2026');
  await page.getByRole('button', { name: 'Add Scholarship' }).click();

  await expect(page).toHaveURL('/scholarships');
});
真正能体现 AI 价值的，往往就是这种有状态、有上下文、有业务语义的真实流程。
11. Selector 策略

好的 AI 输出，仍然依赖稳定的 Selector 策略

优先级 写法 为什么能长期使用
1 getByTestId('submit-button') 这是 UI 和测试之间最稳定的契约。
2 getByRole('button', { name: 'Add Scholarship' }) 语义清晰、可读性强，只要命名设计合理，通常也比较稳。
3 getByLabel('Application Due Date *') 很适合表单字段，也符合可访问性语义。
4 locator('#mui-9') 可以临时使用，但当 ID 由组件库生成时，通常不够稳定。
默认不要 locator('//div/button[1]') XPath 和位置型 selector 很难维护，也不利于 review。
如果 AI 总是在猜错 selector，很多时候问题不在 prompt，而在于前端没有提供稳定的测试契约。
12. 认证状态

工程模式：用 storageState 复用登录态

auth/setup.ts

async function globalSetup() {
  const browser = await chromium.launch();
  const page = await browser.newPage();

  await page.goto('http://localhost:3000/login');
  await page.locator('#user_email').fill('district_manager@example.com');
  await page.locator('#user_password').fill('password');
  await page.locator('input[type="submit"]').click();

  await page.waitForURL(/students/);
  await page.context().storageState({ path: 'auth/user.json' });
  await browser.close();
}

playwright.config.ts

export default defineConfig({
  globalSetup: './auth/setup.ts',
  use: {
    baseURL: 'http://localhost:3000',
    storageState: 'auth/user.json',
    trace: 'on-first-retry',
  },
});
这种项目约定最适合在一开始就定义清楚，然后在所有生成测试中稳定复用。
13. Mocking

Mocking 和数据准备需要明确的默认策略

默认优先使用 API / fixture 方式准备数据，因为它更稳定、更快。 API mocking 主要留给外部依赖或者 UI 状态模拟。 UI 驱动的数据创建 则只保留给关键用户旅程和 smoke tests。

方式 默认定位 原因
API / fixture 造数 首选 更快、更稳定，对 UI 时序依赖更少。
API mocking 选择性使用 适合外部依赖、错误场景和难复现 UI 状态。
UI 驱动创建 有限使用 只在“UI 流程本身就是被验证对象”时才值得花这个成本。

推荐原则

  • 如果 UI 本身不是测试目标，就尽量在 UI 之下完成数据准备。
  • 只有在明确知道原因时才做 mocking，而且要把原因写清楚。
  • 真正走 UI 创建路径的测试，保留一小层 smoke 覆盖即可。

Mock 示例

await page.route('**/api/v1/inventory', route =>
  route.fulfill({ json: mockInventory })
);
这背后的思路其实就是 test pyramid：优先要稳定和速度，只有在确实能提升信心时，才付出 UI 级别的成本。
14. 责任归属

人的责任必须在工作流里保持可见

AI 可以负责

✓ 把明确需求快速转成代码草稿。

✓ 稳定复用既有模式和约定。

✓ 根据执行结果和失败反馈提出修复建议。

✓ 加速补覆盖、扩场景。

人必须负责

✗ 判断哪条流程是真正的业务关键路径。

✗ 判断断言是否足够有意义。

✗ 判断失败是否应该阻断发布。

✗ 判断这条测试长期是否值得信任。

最稳妥的工作模式其实很简单： AI 负责草稿和重复劳动，人负责测试意图和最终判断。

15. 反模式

依然会拖垮 AI 生成测试套件的反模式

不要这样做

await page.waitForTimeout(2000);
await page.$('.btn-primary');
test.only('debug me', async () => {});
let sharedState = [];

更推荐这样做

await expect(locator).toBeVisible();
await page.getByRole('button', { name: 'Submit' });
test('smoke flow', { tag: '@smoke' }, async () => {});
test.beforeEach(async ({ page }) => {
  await page.goto('/cart');
});
AI 不只会放大好习惯，也会放大坏习惯。没有清晰规范时，它只会更快地产生一批脆弱测试。
16. 常见问题

Frequently Asked Questions

AI 能完全自动化 E2E 吗？

AI 的确可以大幅自动化 E2E 测试代码的生成，也能协助维护、迭代和分析。 但在场景设计、prompt 编写、代码评审和复杂结果判断上，人的参与仍然不可替代。

更准确的说法是：这是 AI 辅助自动化，而不是完全自治的 AI 自动化。

AI 会取代测试自动化岗位吗？

不会。更可能发生的是岗位重心变化：实现速度会变快，而测试策略、prompt 设计、 结果分析和质量把关这些能力会变得更重要。

Prompt engineering 和 failure analysis 只会更重要，不会更不重要。

如何开始把 AI 用到 Playwright 自动化中

步骤 动作
1 先把工具链配起来：VS Code、Git、Playwright，以及像 Cline + Playwright MCP 这样的 AI 辅助工具。
2 练习写高质量 prompt，把测试场景拆成清晰、具体、逐步的指令。
3 先从一个简单的 E2E 场景开始，生成代码之后务必亲自验证。
4 确认可靠之后，再把这些生成测试接入仓库和 CI/CD 工作流。
17. 总结

关键结论

1. 先把输入标准化

使用结构化 prompt，或者共享的 agent instruction，让生成测试真正贴合项目约定。

2. 先把契约补齐

稳定 selector、明确 auth 模式，这些都会直接决定 AI 能不能稳定产出可用测试。

3. 用真实流程证明价值

真正能体现 AI 价值的，是 scholarship creation 这类真实业务流程，而不是轻量 catalog demo。

4. 人仍然在 Gate 上

生成测试必须先执行、检查、评审，只有证明了业务价值之后，才应该进入 CI。
