AI for Testing Workshop

Using AI for Testing, with E2E as the Focal Point

AI is already strong at unit and integration test generation. The harder, more valuable conversation is how to use it well for end-to-end testing.

This session starts from the broader topic of AI for testing, then narrows to the highest-friction layer: structured prompt → AI agent / MCP → generated Playwright test → execution → review → CI.

Workshop Objective

Present a practical operating model for generating, reviewing, and scaling automated tests with AI without lowering quality.

Audience

Technical teams adopting AI-assisted test authoring without lowering engineering standards.

Case Study

The local scholarship workflow serves as the primary example instead of relying only on a toy demo.

Core Thesis

AI is a force multiplier for test delivery, but E2E is where workflow design and engineering judgment still matter most.

1. Workshop Framing

Workshop Framing

The Broad Theme

The theme is how to use AI for software testing, not only how to write Playwright code. The objective is to show where AI meaningfully accelerates test work and where human judgment remains essential.

Why E2E Gets the Spotlight

AI is already very good at generating unit tests and integration tests because those layers usually have tighter scope, clearer inputs, and less UI uncertainty. E2E remains the most expensive and most strategic layer.

The framing is not simply “AI can write tests.” It is “AI helps across the stack, but E2E is where a better workflow creates the biggest payoff.”

2. Why E2E

Why E2E Still Matters

Logic

Unit tests prove isolated correctness, but they do not show whether a user can complete the real flow.

Contracts

Integration tests catch system boundaries, but they still stop short of browser behavior and business workflow.

Outcomes

E2E tests validate that a customer journey works from UI intent to backend effect.

If the business value is “a manager can create a scholarship”, then the highest-signal test is the one that verifies that workflow, not only the form reducer or the API client.

3. Cost

Why Traditional E2E Feels Expensive

Common Failure Modes

  • Brittle selectors couple tests to styling details instead of stable intent.
  • Login setup and data setup get copy-pasted into every spec.
  • Async behavior creates race conditions, retries, and false negatives.
  • Teams spend more time repairing tests than expanding workflow coverage.

What Teams Really Pay For

  • Boilerplate authoring time.
  • Slow feedback from repetitive setup steps.
  • Maintenance churn after harmless UI refactors.
  • CI noise that reduces trust in the suite.
The pain is not that E2E is conceptually wrong. The pain is that manual authoring and upkeep do not scale well.
4. What AI Changes

AI Changes the Cost Curve, Not the Definition of Quality

What AI Is Good At

  • Turning a structured requirement into Playwright test scaffolding.
  • Filling in repetitive browser steps and assertions quickly.
  • Refactoring specs to align with shared patterns and conventions.
  • Iterating after a failure when the trace and DOM context are clear.

What AI Does Not Own

  • Choosing the right business scenario to protect.
  • Deciding what should block a release.
  • Knowing whether a generated selector really exists.
  • Understanding whether the test proves user value or just passes.
5. Benefits and Limitations

Benefits and Limitations of AI-Driven E2E Testing

Benefits

  • Speed: test creation becomes much faster when code can be generated from a structured prompt.
  • Accuracy: AI can produce consistent Playwright syntax and reduce routine authoring mistakes.
  • Coverage: lower authoring cost makes it easier to add more scenarios and broaden coverage.
  • Accessibility: detailed Playwright knowledge becomes less critical when prompts and conventions are well defined.
  • Standardization: generated tests are more likely to follow shared formats, patterns, and project practices.

Limitations

  • Prompt quality: vague inputs still produce vague or incorrect tests.
  • Learning curve: effective use still requires E2E testing judgment and prompt design skill.
  • Tool constraints: results are limited by the MCP tooling and the LLM behind it.
  • Debugging: complex failures still require human expertise in Playwright and browser behavior.
  • Over-reliance: generated tests still need review, validation, and ongoing ownership.
The practical model is straightforward: use AI to reduce the cost of authoring, but keep humans responsible for test intent, debugging, and release confidence.
6. Workflow

AI-Assisted E2E Workflow

01
Structured Prompt

Describe feature, goal, steps, data, and expected outcomes with enough precision that the agent is not guessing.

02
AI Agent / MCP

Use browser-aware tooling to inspect the page and produce real Playwright code instead of pseudo-automation.

03
Generated Spec

Output should still be standard TypeScript Playwright tests that engineers can read, edit, and review.

04
Execute

Run against the real app, inspect failures, and verify selectors, timing, and business assertions.

05
Human Review

Confirm the test protects the right workflow and does not encode brittle or misleading assumptions.

06
CI / Release Gate

Commit the spec, run it continuously, and treat it as a production guardrail rather than a one-off experiment.

The key shift is not “AI writes a test.” The key shift is “AI shortens the loop from requirement to reviewable, executable coverage.”
7. Prompt Quality

Prompt Quality Becomes Test Quality

Weak Prompt

Write a Playwright test for scholarships.
Result: generic code, guessed selectors, and incomplete assertions.

Useful Prompt

I need to create an E2E test using the Playwright MCP.

Feature: Scholarship creation
Goal: District manager can create a scholarship
Entry: authenticated user
Path: /scholarships/new
Inputs:
  - name: Test Scholarship
  - amount: 5000
  - due date: 12/31/2026
Assertions:
  - submit succeeds
  - user lands on /scholarships
  - created record appears in list if UI shows it
Constraints:
  - prefer getByRole/getByLabel
  - reuse storageState when possible
Include

Goal, actor, entry state, critical inputs, expected outcomes, and selector preferences.

Do Not Assume

The model already knows the authentication pattern, routing conventions, or form semantics.

8. Prompt Examples

Prompt Patterns Across Test Layers

Unit / Integration Style Prompt

All new code additions should include corresponding unit tests.

When adding new functionality:
* Create test files for new modules to verify core behavior
* Add happy path tests for utility functions
* Test edge cases and different input types where applicable

Examples:
- infer function behavior
- add edge cases
- generate table-driven tests
- mock dependencies when needed
AI is typically strong at this layer because the logic is deterministic and isolated. That makes it easier to infer function behavior, add edge cases, generate table-driven tests, and mock dependencies correctly.

E2E Style Prompt

Feature: Scholarship creation
Goal: District manager can submit a new scholarship
Type: end-to-end test
Precondition:
  - authenticated user via storageState
Route:
  - /scholarships/new
Steps:
  1. Fill scholarship name
  2. Fill amount
  3. Fill application due date
  4. Click Add Scholarship
Assertions:
  - navigation ends at /scholarships
  - no validation errors are shown
Constraints:
  - prefer accessible selectors
  - avoid arbitrary waits
The same model behaves differently across layers. E2E prompts require more context because browser state, selector quality, and workflow semantics all matter.
9. Reusable Prompt

Playwright MCP Prompt Template

I need to create an E2E test using the Playwright MCP.
Please help me generate a test script that I can add to our test suite.

Test details:
- Feature to test: [Feature Name]
- Test description: [Brief Description]
- Base URL: [Application URL]
- Test steps:
  1. Navigate to [Login URL or Specific Page URL]
  2. Log in with credentials and click the login button
  3. Click the "Create New" button
  4. Complete entity setup fields and required selections
  5. Click Next
  6. Enter query or input text
  7. Set a slider or advanced option if needed
  8. Click CREATE
  9. Verify whether a modal is visible
  10. Handle the modal only if it appears
  11. Wait for the created entity to be visible
  12. Upload assets from a test folder if required

IMPORTANT:
- Use the Playwright MCP to generate the test code.
- Add comments for complex logic.
- Ensure browser is closed after test completion.
- Include error handling and timeouts where appropriate.

Save to:
- Path: [tests]/[my_feature_test].spec.ts
- Test Case Name: "Validate My Feature"
Purpose

The template gives the agent a target workflow, state assumptions, branching behavior, file destination, and quality constraints in one request.

Adaptation

Keep the structure fixed, then replace the feature name, route, actions, data values, and expected results for each scenario.

10. Real Example

Anchor the Talk in a Real Business Flow

Repository Example

  • e2e-demo/tests/scholarship.spec.ts already covers scholarship creation.
  • The flow models a real internal role: district manager.
  • The assertions verify navigation after submission and demonstrate form interaction complexity.

Current Spec Shape

test('user can create a scholarship with storage state', async ({ page }) => {
  await ensureLoggedIn(page);

  await page.getByRole('textbox', { name: 'Name of Scholarship *' })
    .fill('Test Scholarship');
  await page.locator('#mui-9').fill('5000');
  await page.getByRole('group', { name: 'Application Due Date' })
    .getByLabel('Application Due Date *')
    .fill('12/31/2026');
  await page.getByRole('button', { name: 'Add Scholarship' }).click();

  await expect(page).toHaveURL('/scholarships');
});
Realistic flows are where AI assistance becomes credible: more state, more setup, more business context, and more measurable savings.
11. Selector Policy

Good AI Output Still Depends on a Stable Selector Strategy

Priority Pattern Why It Scales
1 getByTestId('submit-button') Stable contract between UI and tests.
2 getByRole('button', { name: 'Add Scholarship' }) Readable, semantic, resilient when labels are intentional.
3 getByLabel('Application Due Date *') Strong choice for form fields and accessibility-aligned UIs.
4 locator('#mui-9') Works tactically, but brittle when IDs are generated or design-system driven.
Never by Default locator('//div/button[1]') XPath and positional selectors are hard to maintain and hard to review.
If AI keeps inventing selectors, the fix is usually not “better prompting” alone. The fix is a better frontend test contract.
12. Auth

Operational Pattern: Login Once with storageState

auth/setup.ts

async function globalSetup() {
  const browser = await chromium.launch();
  const page = await browser.newPage();

  await page.goto('http://localhost:3000/login');
  await page.locator('#user_email').fill('district_manager@example.com');
  await page.locator('#user_password').fill('password');
  await page.locator('input[type="submit"]').click();

  await page.waitForURL(/students/);
  await page.context().storageState({ path: 'auth/user.json' });
  await browser.close();
}

playwright.config.ts

export default defineConfig({
  globalSetup: './auth/setup.ts',
  use: {
    baseURL: 'http://localhost:3000',
    storageState: 'auth/user.json',
    trace: 'on-first-retry',
  },
});
This is the kind of project convention that should be defined once and reused consistently across generated tests.
13. Mocking

Mocking and Data Setup Need a Clear Default Policy

We use API / fixture-based data setup as the default for test stability and performance. We use API mocking only for external dependencies or UI state simulation. We reserve UI-driven data creation for critical user journeys and smoke tests.

Approach Default Use Why
API / fixture-based setup Primary choice Fast, deterministic, and less coupled to UI timing.
API mocking Selective choice Best for external dependencies, error simulation, and hard-to-reproduce UI states.
UI-driven creation Limited choice Reserve this approach for cases where the UI flow itself is what needs validation.

Recommended Rule

  • Set up data below the UI whenever the UI is not the subject of the test.
  • Mock only with explicit intent and document the reason.
  • Reserve a small smoke layer for true UI-driven creation paths.

Example Mock Hook

await page.route('**/api/v1/inventory', route =>
  route.fulfill({ json: mockInventory })
);
This follows a test pyramid mindset: prioritize reliability and speed, then pay the UI cost only where it adds confidence.
14. Ownership

Human Ownership Must Stay Visible in the Workflow

AI Can Own

✓ Translating clear requirements into starter code.

✓ Repeating established patterns consistently.

✓ Suggesting fixes after execution feedback.

✓ Accelerating coverage expansion on known flows.

Humans Must Own

✗ Whether the workflow is business-critical.

✗ Whether the assertions are meaningful enough.

✗ Whether failures should block deployment.

✗ Whether the test remains trustworthy over time.

The strongest operating model is simple: AI owns the draft and the repetition. Engineers own the intent and the verdict.

15. Anti-Patterns

Anti-Patterns That Still Kill AI-Generated Test Suites

Do Not Ship This

await page.waitForTimeout(2000);
await page.$('.btn-primary');
test.only('debug me', async () => {});
let sharedState = [];

Prefer This

await expect(locator).toBeVisible();
await page.getByRole('button', { name: 'Submit' });
test('smoke flow', { tag: '@smoke' }, async () => {});
test.beforeEach(async ({ page }) => {
  await page.goto('/cart');
});
AI can reproduce bad habits at scale. Conventions and review are what stop acceleration from becoming amplified fragility.
16. FAQ

Frequently Asked Questions

Can E2E Testing Be Fully Automated with AI?

AI can significantly automate the generation of E2E tests and assist with maintenance, iteration, and analysis. However, human oversight remains essential for scenario design, prompt quality, code review, and interpretation of complex results.

In practice, this is AI-assisted automation rather than full AI autonomy.

Will AI Replace Test Automation Roles?

No. AI is more likely to transform the role by accelerating implementation and shifting more value toward test strategy, prompt design, result analysis, and quality ownership.

Prompt engineering and failure analysis become more important, not less.

How to Start with AI for Playwright Automation

Step Action
1 Set up the toolchain: VS Code, Git, Playwright, and an AI assistant such as ClaudeCode with Playwright MCP.
2 Learn to write strong prompts by breaking a scenario into explicit, step-by-step instructions.
3 Generate a first test for a simple E2E flow, then verify the produced Playwright code.
4 Integrate validated tests into the repository and CI/CD workflow.
17. Takeaways

Key Takeaways

1. Standardize Input

Use structured prompts or a shared agent instruction file so generated tests reflect actual project conventions.

2. Strengthen Contracts

Add stable selectors and explicit auth patterns so AI works with the system instead of guessing around it.

3. Keep Humans in the Gate

Execute, inspect, review, and promote generated tests into CI only after they prove business value.
